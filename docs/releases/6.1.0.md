# borgmcp 6.1.0

Batch startup now puts non-human-seat drones in a shared tmux session and opens
the human-seat drone in a separate terminal. This applies to `borg launch-all`
and the roster launched by `borg quickstart`. The human seat is the role that
speaks with the human's authority.

## Startup and fallback behavior

- Each non-human-seat drone gets its own window in the `borg-<cube>` tmux session.
  All eligible drones still start, including the human-seat drone.
- If tmux is missing, the entire batch uses terminal windows or tabs. If a
  required terminal is unavailable, Borg prints manual launch commands before
  starting any sessions; quickstart reports that no sessions launched.
- Current server identity determines which drones hold the human seat. When
  identity cannot be confirmed, the drone opens in a terminal rather than using
  potentially stale role metadata to put it in tmux.
- Linux automatic terminal launches require an X11 or Wayland display. Terminal
  processes start without waiting for their drone sessions to exit, allowing
  the complete batch to start concurrently.
- Explicit `--mode tmux`, `--mode terminals`, and `--mode pastelist` continue to
  select one destination for the entire batch. Explicit tmux mode still fails
  with installation guidance if tmux is missing.
- `--dry-run` shows each drone's destination. Existing live-session and invalid
  session skips remain in effect. `--no-attach` leaves tmux detached.

See [Batch startup](https://github.com/Byte-Ventures/borg-mcp-client/blob/v6.1.0/docs/BATCH_STARTUP.md) for the complete behavior.

## Dependency updates

- Raise the runtime MCP SDK minimum to 1.32.1 to include its published security
  fixes. The locked `proxy-addr` dependency also advances to 2.0.8.
- Update development tooling to Vitest 4.1.12, Vite 8.3.5, and `source-map-js`
  1.2.2, removing the vulnerable Tinypool dependency. The Node.js floor remains
  22.13.0. Test isolation still fails the process if operator state is modified.

The transitive versions above describe the lockfile tested for this release.
Consumer installs resolve transitive dependencies within their declared ranges;
the package does not include an npm shrinkwrap.

## Upgrading

Run `borg update`. The shared contract pin remains `borgmcp-shared` 2.2.0;
no server or shared-package release is required for this client change.
