# borgmcp 6.3.1

Fixes forced launches of saved drone worktrees. In 6.3.0, `borg launch-all
--cli codex --force` bypassed the batch's launch-marker check but could still
be refused by the child launcher's live inbox-monitor check.

## Launch fixes

- Passes an explicit `--force` through tmux, terminal, and printed commands to
  the targeted drone launcher and its child process. For one drone, use
  `borg launch <drone-label-or-id-prefix> --cli codex --force`.
- Keeps the expected-drone identity and completed-registration checks in place
  when forcing a launch.
- Reports how many launch commands were sent and the requested CLI. Recent
  roster activity is no longer labeled as proof that the new session started;
  it can come from an older session for the same drone.

## Clearer startup guidance

Existing windows stay open. Closing the terminal displaying tmux detaches from
the session; its drones keep running. To reconnect, copy the exact attach
command printed by `borg launch-all`.

Launch markers expire after five minutes. Another session can then start even
without `--force`, particularly for Codex, which has no inbox-monitor guard.
Stop existing sessions before relaunching or switching CLIs. `--force` bypasses
marker and inbox-monitor checks and can create duplicate sessions. Check each
new window for startup errors or folder-trust prompts.

## Upgrading

Run `borg update`. The Node.js minimum remains 22.13.0 and the shared contract
remains pinned to `borgmcp-shared` 2.2.0. No server or shared-package release is
required for this client patch.
